2 — SUPABASE : METTRE À JOUR LA FONCTION workshop-recovery
Il faut aussi déployer la modification serveur pour obtenir les codes courts.
Mettre les fichiers sur GitHub ne déploie pas une Edge Function Supabase.
- Supabase > Edge Functions > workshop-recovery > Code.
- Ouvre le fichier de cette archive :
    supabase/functions/workshop-recovery/index.ts
- Remplace tout le code de la fonction par ce fichier index.ts.
- Clique Deploy updates et attends la réussite.
- Laisse la vérification automatique JWT désactivée pour CETTE fonction,
  comme en MAJ117. Le formulaire de récupération fonctionne avant connexion ;
  la fonction vérifie elle-même le code, les limites de tentatives et, pour
  générer un code, la session et le mot de passe actuel.
Ne change pas les réglages des autres fonctions. workshop-accounts conserve
la version117 déjà déployée : son code n'a pas été modifié dans cette MAJ.

Les nouveaux codes contiennent exactement 8 caractères, chiffres et lettres
majuscules sans I,L,O,U pour limiter les confusions. Ils restent personnels,
à usage unique, valables un an, stockés sous forme d'empreinte uniquement.
Ils se génèrent dans Mon profil > Récupération de mon compte.
Les anciens codes longs restent acceptés jusqu'à leur utilisation,
remplacement ou expiration : personne n'est obligé d'en recréer immédiatement.
Le mot de passe reste de 12 caractères minimum : seul le code est raccourci.

Protection supplémentaire des nouveaux codes : empreinte HMAC liée à une clé
serveur. Aucun secret n'est transmis à l'application ou inscrit dans le SQL.
Par défaut la fonction utilise SUPABASE_SERVICE_ROLE_KEY, déjà fournie par
Supabase. Si tu changes cette clé serveur, les codes courts générés avec elle
ne fonctionneront plus : ils devront être régénérés. Les mots de passe restent
inchangés et la réinitialisation par le responsable est conservée.
Option facultative pour dissocier cette empreinte d'une rotation de service_role :
RECOVERY_CODE_SECRET dans Edge Functions > Secrets, à définir AVANT de générer
les premiers codes courts, puis à conserver. Ce réglage n'est pas requis.
Ne mets jamais de clé serveur ou de code personnel dans GitHub ou une variable VITE.

4 — CE QUI CHANGE
SIGNALEMENTS
Pour l'administrateur et les modérateurs, les dossiers Mes signalements et
Signalement de mon équipe sont sous la recherche et au-dessus des fiches.
Le dossier de l'équipe continue d'exclure les signalements personnels.

RÉCAPITULATIF
Le récapitulatif et sa fenêtre du matin affichent automatiquement le nombre
de signalements créés pendant la journée concernée, ou explicitement zéro.
Le comptage utilise les heures de Paris et inclut les signalements créés après
la préparation du récapitulatif le soir. Ce sont les fiches encore conservées
dans la base ; ce n'est pas un journal des fiches définitivement supprimées.
Le lundi, le récapitulatif du samedi indique les signalements du samedi.
Aucune anomalie ou pièce manquante n'est réintroduite.

PLAN AUTOMATIQUE
Chaque jour à partir de 05:00 heure de Paris, un brouillon est généré côté
Supabase, même quand personne n'a ouvert l'application. Le programme passe
toutes les 10 minutes. Si aucun horaire n'est encore importé, il attend un
prochain passage. Une journée sans horaires ne génère pas un plan vide.
Les changements d'heure été/hiver sont pris en compte.

L'assistant utilise :
- collaborateurs actifs prévus présents, avec une durée de travail positive ;
- compétences Autonome dans la matrice ;
- équipes Encadrants réservées aux postes de bureau/gestion, autres techniciens
  sur les postes techniques ;
- exclusion des congés/absences acceptés, comptes suspendus, invités/directeurs ;
- exclusion des postes désactivés et ponts en panne ou bloqués ;
- priorité aux postes avec peu de candidats, puis préservation des compétences
  polyvalentes utiles et prise en compte de l'amplitude de travail.
Une seule affectation principale automatique par personne. La géométrie et
les autres ajustements manuels existants restent disponibles.

Il ne touche jamais aux affectations publiées dans workshop_days.
Un brouillon déjà préparé ou un plan déjà affecté est conservé.
Après annulation ou publication, le programme ne recrée pas un brouillon
pour la même date. Tu peux toujours en préparer un manuellement ensuite.
Si les horaires/compétences changent après la génération, vérifie le brouillon ;
si nécessaire annule-le puis utilise Préparer ce plan et Générer une proposition.
Le brouillon initial n'est pas recalculé automatiquement en écrasant tes choix.

L'administrateur ou le modérateur doit vérifier les horaires et le plan, corriger
si nécessaire, puis cliquer Publier le plan. Avant cela les collaborateurs
continuent de voir uniquement le dernier plan publié.
La proposition n'est pas une optimisation de la couverture heure par heure :
un poste affecté à une personne à temps partiel n'est pas forcément couvert
toute la journée. Les postes non couverts restent signalés pour contrôle.
Aucune IA ni API payante n'est utilisée.

5 — VÉRIFICATIONS APRÈS INSTALLATION
- Signalements : recherche, puis les 2 dossiers, puis les fiches.
- Mon profil : génère un code, conserve-le en lieu sûr ; il contient 8 caractères.
  Ne le communique à personne. Un ancien code reste utilisable.
- Récapitulatif : ouvre une journée ayant des signalements ; le nombre apparaît.
- Supabase > Cron : vérifier que atelier-plan-brouillon-118 est actif, sans doublon,
  et que son historique ne comporte pas d'erreur.
- Sur une journée avec horaires/compétences et sans plan ni brouillon existant,
  le prochain passage après 05:00 prépare le brouillon. Il apparaît dans le plan
  administrateur/modérateur grâce à la synchronisation habituelle de 20 secondes.
- Vérifie que le plan collaborateur ne change qu'après Publier le plan.
Si Supabase est en pause ou indisponible, Cron ne peut pas travailler : la
préparation attendra la remise en route de l'infrastructure.

Le rapport VERIFICATIONS-118.md détaille les tests et leurs limites.
