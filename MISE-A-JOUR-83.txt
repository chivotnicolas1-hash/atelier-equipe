ATELIER FAYET 33 — MISE À JOUR 83
Version affichée dans l’application : V1.0
Cette archive remplace les fichiers du projet après la mise à jour 82.

INSTALLATION — RESPECTER CET ORDRE
1. Dans Supabase > SQL Editor, ouvrir une nouvelle requête.
2. Copier tout le contenu de supabase/83a-messages-conges.sql, puis Run.
   Attendre Success avant de continuer.
3. Faire de même avec supabase/83b-consommables.sql.
4. Faire de même avec supabase/83c-taches-communes.sql.
   Les trois scripts peuvent être réexécutés. Si une erreur apparaît,
   arrêter et transmettre le message complet avant de déployer le site.
5. Décompresser cette archive. Remplacer les fichiers du projet GitHub
   par ceux fournis : src, public, supabase, index.html, package.json,
   package-lock.json, tsconfig.json, vite.config.ts, postcss.config.js.
   Conserver les variables de build Cloudflare existantes.
   Ne jamais ajouter de fichier _redirects.
6. Avec GitHub Desktop : vérifier les changements, Commit puis Push.
   Attendre la réussite du déploiement Cloudflare, fermer et rouvrir l’app.

Aucune nouvelle clé API ni facturation IA n’est nécessaire.
Pas de nouvelle Edge Function à déployer pour cette mise à jour.
Le programme de notifications déjà installé doit rester actif : il traite
les messages programmés avec le système d’envoi existant. Les notifications
mobiles nécessitent toujours un abonnement actif sur l’appareil.
Les fichiers de tests, dépendances et anciennes instructions de mise à jour
ne sont pas inclus. Conserver une sauvegarde de la version précédente.

MESSAGES ENTRE ENCADRANTS
Dans Mes notifications, ouvrir « Messages programmés entre encadrants ».
L’administrateur et les membres actifs de l’équipe Encadrants peuvent
choisir les destinataires, écrire un message et programmer sa date/heure.
Les horaires sont interprétés en heure de Paris. Un message non envoyé
peut être modifié ou supprimé par son auteur. À l’échéance : notification
interne et envoi mobile via le système existant, sans doublon de traitement.
Un compte désactivé ou qui n’est plus éligible n’est pas notifié.

INVITÉ
Accès aux pages collaborateurs en lecture seule, avec les démonstrations
existantes (horaires, affectation et fiche de signalement). Les congés et
BT à reprendre disposent de fiches fictives. Aucune demande réelle n’est
créée par les boutons du compte invité. Les fonctions d’administration
ne deviennent pas accessibles à ce rôle.

SIGNATURE ET CONGÉS
Quand l’administrateur retire une signature via l’interface prévue, le
collaborateur reçoit : « Signature non conforme, merci de renouveler ».
Le calendrier des congés de l’équipe apparaît uniquement dans l’espace
administrateur > Demande de congés. Ouvrir le cadre, choisir le mois,
puis un jour pour voir les noms complets. Jaune : en cours ; vert : validé ;
rouge : refusé. Les propositions/en attente de signature restent en cours.
Le prénom, le nom et le centre/service ne sont éditables que par
l’administrateur. Cette protection est aussi appliquée dans la base.

TÂCHES COMMUNES ET RÉCAPITULATIFS
L’administrateur et les modérateurs peuvent créer, modifier et supprimer
les tâches communes depuis leur espace de gestion et fixer une échéance.
Les cases cochées sont conservées lors d’une modification. Une modification
concurrente impose de rouvrir la tâche plutôt que d’écraser les changements.
La partie « pièces manquantes » n’est plus affichée dans les récapitulatifs ;
les anciennes données ne sont pas effacées. La touche Entrée crée une
nouvelle puce dans les champs concernés et la lecture utilise une liste.

CONSOMMABLES
- L’ouverture de « Modifier la liste » ne place plus le curseur dans
  un champ de saisie : toucher le champ pour ouvrir le clavier mobile.
- Les catalogues gardent leur ordre de position enregistré, indépendamment
  du nombre de commandes. Le classement dédié reste séparé.
- Les codes de la première colonne des trois PDF sont intégrés : 113 codes.
  Ils ne sont renvoyés qu’aux administrateurs/modérateurs et sont affichés
  dans la modification d’une commande. Une association est faite par
  section/désignation puis conservée par identifiant de produit.
  Un article renommé avant l’installation ou absent des PDF peut afficher
  « Non associé » : aucun code n’est inventé.
- Un article déjà présent déclenche l’avertissement demandé avant l’ajout
  de quantité. Annuler laisse la commande inchangée.
- Lors des prochaines validations, les articles indiqués en rupture sont
  reportés dans la prochaine commande hebdomadaire ouverte. Une commande
  future existante est réutilisée. Les quantités se cumulent si l’article
  y figure déjà. Une même ligne source n’est reportée qu’une fois, même si
  la commande est validée à nouveau après correction. Les commandes déjà
  validées avant cette installation ne sont pas retraitées automatiquement.
  Si la limite de 100 lignes ou de 999 unités est dépassée, la validation
  est arrêtée avec une erreur, sans perte silencieuse d’articles.
- Le marquage RUPTURE sur le plan d’huile est plus petit. Dans l’espace
  de gestion des huiles, l’administrateur et les modérateurs peuvent lever
  une rupture. Cela réactive le produit du catalogue ; vérifier séparément
  la case rupture d’une ligne déjà enregistrée dans une commande.

VÉRIFICATIONS RÉALISÉES
Compilation TypeScript et production réussies. Tests locaux des migrations
réexécutées, droits, messages programmés, absence de doublons, calendrier,
identité des congés, notification de signature, codes privés, ordre du
catalogue, report des ruptures, réactivation des huiles et tâches communes.
Contrôles d’interface aux largeurs 390 et 1280 pixels : messages, calendrier,
édition des tâches communes, invité en lecture seule et listes à puces.
Ces vérifications utilisent une base de test et des données simulées.
La base Supabase et le site Cloudflare de production n’ont pas été modifiés.
