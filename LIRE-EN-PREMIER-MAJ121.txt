ATELIER FAYET 33 — MAJ121
Présences, corrections de déchets et protection des sessions mobiles
Base : MAJ120 déjà installée. Préparée le 23 novembre 2026.
Aucune modification de production ni aucun déploiement effectués ici.

1 — PRÉSENCES CONFIRMÉES / WORKORDER
La dernière définition SQL fournie confirme déjà la présence d'un collaborateur
présent avec des horaires, même sans poste affecté. Cette règle est conservée :
aucune réécriture du moteur des présences n'est nécessaire dans cette livraison.

Le compteur et sa liste utilisent désormais la même sélection :
- collaborateurs actifs, présents sur la journée, avec au moins un horaire valide ;
- présence réellement confirmée en base ;
- administrateurs et modérateurs inclus ; invités et directeurs exclus ;
- une seule ligne par personne, même si elle intervient sur deux pôles.
Les personnes sans affectation sont incluses si elles ont leurs horaires et ont
confirmé leur présence. Les confirmations ne sont pas créées artificiellement.

À chaque clic WorkOrder de la journée courante, la confirmation est revérifiée
côté serveur, même si l'écran affichait déjà une ancienne confirmation. Le serveur
conserve le premier horodatage : pas de nouvelle présence à chaque clic.
Le verrou anti-double-clic, l'ouverture après succès et l'absence de message de
pointage sont conservés. Les autres dates affichées ne sont pas confirmées à tort.
Les règles horaires existantes des gestionnaires restent inchangées : pas de
nouvelle confirmation hors de leurs créneaux prévus.

Le retour depuis le cache de navigation mobile déclenche le même rafraîchissement
commun que le retour au premier plan. Le cycle de 20 secondes reste inchangé ; aucun
second minuteur n'a été ajouté. Les affectations et le plan classique sont conservés.

2 — DÉCHETS : DATES ET QUANTITÉS
Défaut identifié dans la fonction fournie workshop_update_waste_v60 : une correction
réinitialisait les champs de validation et de collecte. Une nouvelle validation
pouvait alors déplacer le point de départ du délai de ramassage.

La correction remplace uniquement cette fonction centrale. Un administrateur ou
modérateur peut continuer à modifier chaque quantité, le contenu et les précisions,
mais les informations suivantes restent inchangées :
- date et auteur de création ;
- validation initiale, son auteur et sa date ;
- date et auteur du ramassage déjà enregistré ;
- relances et ramassages partiels ;
- date de collecte annoncée par le prestataire, gérée séparément.
Une correction d'une demande déjà collectée ne la rouvre plus.
Une demande non validée ne devient pas validée par une simple modification.
Les contrôles de version concurrente, d'unité, de quantité et de prestataire restent
actifs. Les collaborateurs ne gagnent pas le droit de modifier une demande validée.

L'enregistrement d'une relance conservait déjà les dates initiales dans la définition
fournie : ce chemin est testé et conservé. Une relance possède sa propre date/heure.
Le délai ouvré reste calculé à partir de la validation initiale, du lundi au vendredi,
hors jours fériés. La modification des réglages de délai reste une action distincte.

Le formulaire de modification rappelle les dates initiales pour éviter de les
confondre avec la date de dernière correction.
La mise à jour ne peut pas reconstituer une date déjà effacée par une ancienne
modification ; elle ne réécrit pas les anciennes demandes à l'installation.

3 — CONNEXION : PROTECTION AJOUTÉE ET LIMITES
Les mots de passe sont déjà traités par Supabase Auth : empreintes bcrypt salées,
non stockage d'une copie déchiffrable. Ce mécanisme reste intact.
Les échanges de l'application et de Supabase utilisent leurs adresses HTTPS.
L'en-tête HSTS est ajouté sur l'application pour imposer HTTPS au navigateur après
réception de cet en-tête. Les protections de MAJ120 sont conservées.

Sur mobile, les jetons de session et de renouvellement persistants sont désormais
chiffrés localement avec AES-GCM 256 bits :
- clé générée sur l'appareil, non exportable via Web Crypto ;
- clé conservée dans IndexedDB, jamais dans GitHub ou les variables Cloudflare ;
- IV aléatoire par écriture et authentification du contenu ;
- données liées au projet et à leur clé de stockage ;
- migration automatique des anciennes entrées Auth locales, puis suppression de
  leurs anciennes copies en clair ;
- effacement et marqueur local de déconnexion pour éviter de restaurer une ancienne
  copie après un problème de stockage.
Les autres préférences (thème, affichage, etc.) ne sont pas des mots de passe et
restent dans leurs emplacements habituels.

Si le navigateur refuse ce stockage, aucun repli vers une session persistée en clair
n'est ajouté : la session est temporaire en mémoire et un message l'indique.
Une nouvelle connexion peut être nécessaire après fermeture. Effacer les données
du navigateur supprime aussi sa session locale ; le compte Supabase n'est pas supprimé.
Sur PC, les sessions restent en mémoire, sans nouvelle persistance : la déconnexion
à la fermeture/recharge est conservée.
Aucun mot de passe ni code de récupération n'est ajouté au stockage de l'application.
Le code de récupération existant, les secrets et les limitations restent inchangés.

IMPORTANT : aucun système ne peut être garanti « inviolable ». Ce chiffrement
protège le stockage local, pas un appareil compromis ni un script malveillant
exécuté dans l'application. Le navigateur doit pouvoir utiliser la clé et les jetons
pendant une session. Ce n'est pas un chiffrement de bout en bout de toutes les données
Supabase. Les ID administrables restent des identifiants, pas des secrets chiffrés
champ par champ. Les autorisations serveur restent indispensables. Aucune clé de
service n'est mise dans le site. Aucun service ni abonnement payant n'est ajouté.

4 — SQL À EXAMINER AVANT EXÉCUTION
supabase/121-corrections-dechets.sql :
- exige les prérequis MAJ120/déchets112 ;
- sauvegarde une seule fois l'ancienne définition dans une petite table privée
  workshop_private.code_backup121, avec RLS et sans accès client ;
- remplace la fonction de correction des déchets et conserve les contrôles serveur ;
- n'altère aucun enregistrement métier au moment de l'installation ;
- exécution en transaction et script réexécutable.
Aucune migration des mots de passe ou des présences n'est effectuée.
Ce SQL n'a pas été appliqué à ton projet lors de la préparation.

5 — INSTALLATION
A. Conserver le ZIP MAJ120 avant intervention.
B. Après lecture/validation, dans Supabase > SQL Editor, exécuter EN ENTIER :
   supabase/121-corrections-dechets.sql
C. Dans une nouvelle requête, exécuter :
   supabase/121-verification-lecture-seule.sql
   Attendu : correction_dates_dechets=true, sauvegarde=1,
   fonction_dechets_anonyme=false, fonction_dechets_connectee=true.
   Les compteurs sont ceux du jour réel en base ; aucune confirmation n'est créée
   par la vérification. Un compteur à zéro peut être normal selon la journée.
D. Remplacer les sources et configurations du projet GitHub par celles de ce ZIP,
   puis attendre la réussite du déploiement Cloudflare.
   Conserver toutes les variables de build existantes et WORKSHOP_ALLOWED_ORIGINS.
   Les fonctions Edge ne changent pas : aucun nouveau déploiement de fonction Edge
   ni nouveau secret n'est nécessaire pour MAJ121.
   Aucun fichier _redirects à ajouter. Ne pas envoyer node_modules ni dist.
E. Fermer puis rouvrir l'application et vérifier sur ton compte :
   - connexion et maintien de session après fermeture/réouverture sur mobile ;
   - WorkOrder, compteur confirmé et liste correspondante côté gestionnaire ;
   - modification d'une quantité de déchets et dates initiales inchangées ;
   - relance avec son propre horodatage, sans décalage du délai initial ;
   - déconnexion sur PC toujours conforme au fonctionnement antérieur.
Une reconnexion peut être nécessaire pendant la migration locale ou après effacement
du stockage du navigateur. Aucun faux utilisateur ou faux déchet n'est ajouté.

6 — RETOUR EN ARRIÈRE
Restaurer les sources MAJ120 redonne l'ancienne interface. Les sessions chiffrées
MAJ121 ne sont pas copiées en clair pour cette opération : une reconnexion mobile
sera nécessaire. La correction SQL indépendante continue de conserver les dates.
La définition précédente de la fonction déchets est sauvegardée en privé pour
préparer un retour ciblé après revue ; ne pas supprimer les demandes ni réinstaller
un ancien SQL au hasard. Les données et le moteur du plan MAJ120 sont conservés.
