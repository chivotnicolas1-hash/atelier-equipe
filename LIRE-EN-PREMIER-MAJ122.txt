ATELIER FAYET 33 — MAJ122
Notifications du récapitulatif selon les horaires des encadrants
Base : MAJ121. Finalisation du 24 novembre 2026.
Aucun déploiement ni changement de production effectué ici.

1 — NOUVELLE RÈGLE
Les heures d'envoi habituelles sont conservées, heure de Paris :
- SOIR : à partir de 18 h 30, « Pense à faire ton récapitulatif », uniquement
  à l'encadrant dont le dernier créneau termine le plus tard sur cette journée.
  Aucun rappel si un récapitulatif de cette journée existe déjà.
- MATIN : à partir de 7 h 30, quand le récapitulatif est disponible, uniquement
  à l'encadrant dont le premier créneau commence le plus tôt sur cette journée.
  Le récapitulatif du samedi reste publié le lundi, pas le dimanche.

S'il n'y a qu'un encadrant éligible avec des horaires, il est le destinataire.
En cas d'égalité d'horaire, le nom puis l'identifiant départagent les personnes,
afin de conserver UN SEUL destinataire. Les coupures déjeuner sont prises en
compte : début du premier créneau et fin du dernier créneau de la journée.
L'envoi reste à l'heure habituelle, même si ce début ou cette fin de poste est à
une autre heure. La réception sur téléphone dépend aussi du navigateur et du réseau.

Encadrants éligibles : équipe Encadrants, rôle administrateur ou modérateur,
compte associé confirmé, fiche active non suspendue, présence prévue « présent »,
horaires valides et absence de congé accepté sur la journée. Un collaborateur,
un invité ou un directeur ne reçoit pas de nouveau droit par cette sélection.
La confirmation WorkOrder n'est pas nécessaire pour être choisi : le destinataire
du matin doit pouvoir recevoir son rappel avant d'ouvrir l'application.

S'il n'y a personne d'éligible, aucune personne sans horaires n'est choisie par
défaut. Le programme réessaie lors des passages suivants de cette journée, par
exemple après un import d'horaires tardif. S'il n'y a pas de récapitulatif publié,
aucune notification de disponibilité n'est inventée.

Le destinataire est fixé au premier passage qui enregistre le message. Un changement
ultérieur d'horaires ne provoque pas une deuxième notification à une autre personne.
Le message apparaît dans Mes notifications et utilise le mécanisme push existant
pour les appareils inscrits de cette même personne. « queued » dans le suivi signifie
message enregistré et éventuelle mise en file, pas preuve de réception sur le téléphone.
Les autres encadrants conservent leur accès habituel aux récapitulatifs ; les règles
de lecture et le popup existant ne sont pas modifiés.

2 — PAS DE NOUVELLE VALIDATION DES DÉCHETS
Le correctif MAJ121 déjà installé est conservé : modifier les quantités ou les
informations d'une demande validée ne remet pas la demande en attente.
Cela reste vrai avant une relance et après une relance.
La date de validation initiale, son auteur, la création, les ramassages déjà
renseignés et les relances sont conservés. L'échéance calculée sur la validation
initiale n'est pas repoussée par une correction.
Une demande non validée ne devient pas validée par une simple correction.
Les collaborateurs ne gagnent pas le droit de modifier une demande validée.
Le formulaire rappelle désormais explicitement qu'une validation est conservée.
Ce fonctionnement a été retesté sur les fonctions fournies.

3 — CE QUE LE SQL CHANGE
supabase/122-notifications-recapitulatif.sql :
- vérifie les prérequis et la présence de la correction déchets MAJ121 ;
- sauvegarde une seule fois l'ancienne routine de routage du récapitulatif dans
  workshop_private.code_backup122 ;
- ajoute workshop_private.recap_dispatch122, petit journal privé de décision ;
- ajoute deux fonctions privées de sélection/enregistrement et remplace seulement
  la routine récapitulatif existante schedule_messages_before49(timestamptz) ;
- conserve la chaîne de programmation des autres notifications ;
- conserve la tâche de notifications existante : aucun nouveau Cron, secret ou
  appel à une API externe ;
- ne supprime ni ne réécrit de demande, récapitulatif, horaire ou notification.
Les nouvelles tables ont RLS activée et aucun accès client direct.
Les nouvelles fonctions ne sont pas exécutables directement par les rôles clients.
L'installation est transactionnelle et réexécutable.

Aucun envoi n'est déclenché par le script d'installation. La routine existante
utilisera la nouvelle règle à son prochain passage normal.
Un message déjà enregistré par l'ancien système n'est pas réémis. Les notifications
déjà parties vers les téléphones ne sont pas rappelées ni supprimées. Le nouveau
ciblage s'applique aux prochains enregistrements, normalement dès la prochaine journée.

4 — INSTALLATION
A. Conserver l'archive MAJ121.
B. Après examen, exécuter EN ENTIER dans Supabase > SQL Editor :
   supabase/122-notifications-recapitulatif.sql
C. Dans une nouvelle requête, exécuter :
   supabase/122-verification-lecture-seule.sql
   Attendu : routine_recap_installee=true, sauvegardes_definitions=1,
   dechets_validation_conservee=true, fonctions_privees_verrouillees=true.
   Les noms matin/soir sont des choix indicatifs selon les horaires actuellement
   présents ; null signifie qu'aucune personne n'est éligible.
   decisions_recentes peut être vide avant le premier passage utile : c'est normal.
   La vérification ne crée aucune notification et ne marque personne comme présent.
D. Remplacer les fichiers du projet GitHub par ceux du ZIP, puis attendre le succès
   du déploiement Cloudflare. Les deux changements visuels sont de simples précisions
   de texte dans Récapitulatif et le formulaire de modification des déchets.
   Conserver les variables de build et les secrets existants.
   Aucun redéploiement des fonctions Edge, aucune clé à générer, aucun _redirects.
E. Après réouverture : vérifier la page Récapitulatif et qu'une demande de déchets
   validée reste validée après correction de ses quantités puis après une relance.
   Le SQL de vérification permet de contrôler les choix des prochaines notifications,
   sans attendre l'heure d'envoi ni créer un faux message dans la production.

5 — RETOUR EN ARRIÈRE ET LIMITES
Revenir aux seuls fichiers GitHub MAJ121 ne restaure pas l'ancien routage serveur.
L'ancienne définition est sauvegardée pour préparer, si nécessaire, un retour SQL
ciblé après revue. Ne pas supprimer de données ou relancer de vieux scripts au hasard.
Le journal reste privé et peut être conservé pour éviter de réémettre un ancien rappel.
Les droits, le chiffrement local des sessions de MAJ121, le plan et le glisser-déposer
sont conservés. Pas de nouvelle dépendance ni de service payant.
Le programme Cron, le worker push et la réception sur de vrais appareils n'ont pas
été testés en production ici. Le contrôle SQL est à effectuer après installation.
